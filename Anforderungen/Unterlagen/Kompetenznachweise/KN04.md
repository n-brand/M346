# KN04: OpenTofu II – Netzwerk als Code

Beachten Sie die [allgemeinen Informationen zu den Abgaben](../Abgaben.md).

**Richtzeit:** ca. 4 Lektionen

Bisher hat AWS die Netzwerk-Entscheidungen für Sie getroffen: Ihre Instanzen landeten «irgendwo» in einem Standard-Subnetz mit zufälligen IPs. In dieser Kompetenz übernehmen Sie die Kontrolle – Sie planen Ihr Netzwerk und bauen es vollständig als Code: eigenes Subnetz, feste private IPs, saubere Security Groups und eine statische öffentliche IP. Das ist die Grundlage für alles Weitere: Ab KN06 trennen Sie Web- und Datenbankserver, und spätestens dann muss das Netzwerk sitzen.

**Das Szenario:** Sie bauen das Netzwerk für eine klassische Zwei-Server-Architektur, wie sie hinter vielen Webapplikationen steckt: ein **Webserver**, der aus dem Internet erreichbar ist, und ein **Datenbankserver**, der nur intern – ausschliesslich vom Webserver aus – erreichbar sein darf. Die Datenbank-Software selbst installieren Sie erst in KN06 (Ansible); hier bauen Sie bereits das Netzwerk und die Sicherheitsstruktur dafür. Deshalb heissen Ihre beiden Instanzen `web` und `intern`: `intern` ist der Platzhalter für die spätere Datenbank-Instanz – Port 3306 (Standardport von MySQL/MariaDB) taucht deshalb schon jetzt in den Security-Group-Regeln auf, obwohl noch keine Datenbank läuft. Halten Sie sich dieses Bild – Webserver aussen, Datenbankserver innen – für den ganzen Auftrag vor Augen, insbesondere für Ihren Netzwerkplan in Teil A.

**Theorie zu dieser Kompetenz:** [Netzwerk und Sicherheit](../Theorie/NetzwerkSicherheit.md) · [OpenTofu](../Theorie/OpenTofu.md)

## B) Das Netzwerk als Code (50%)

Jetzt bauen Sie den Netzwerkplan – vollständig in OpenTofu, in einem neuen Projekt `KN04/`.

### B1) Subnetz und Datenquelle

Ihr Subnetz entsteht **in** der bestehenden Standard-VPC. Deren ID kennen Sie aber nicht (und sie ist bei jedem Lernenden anders) – hartcodieren wäre also falsch. Dafür gibt es in OpenTofu **Datenquellen** (`data`): Sie *lesen* bestehende Ressourcen, statt sie zu erstellen.

```hcl
data "aws_vpc" "default" {
  default = true
}

resource "aws_subnet" "kn04" {
  vpc_id                  = data.aws_vpc.default.id
  cidr_block              = "<Ihr Gruppen-CIDR>"
  map_public_ip_on_launch = true   # Instanzen in diesem Subnetz bekommen eine öffentliche IP

  tags = { Name = "Sub-KN04-<Gruppe>" }
}
```

Erklären Sie in Ihrer Doku: Was ist der Unterschied zwischen `data` und `resource`? Was zeigt der Plan für den `data`-Block an?

**Abgaben (B1):**

- Erklärung in Ihrer Doku: Was ist der Unterschied zwischen `data` und `resource`? Was zeigt der Plan für den `data`-Block an?

### B2) Zwei Security Groups mit unterschiedlich strengen Regeln

- **SG-Web**: eingehend Port 22 und 80 von überall (0.0.0.0/0).
- **SG-Intern**: eingehend Port 22 von überall (Administration), Port 3306 **nur von der SG-Web** – nicht von 0.0.0.0/0, nicht einmal vom ganzen Subnetz. Verwenden Sie dazu `security_groups = [aws_security_group.web.id]` in der Ingress-Regel statt `cidr_blocks`.

Die 3306er-Regel ist die praktische Umsetzung der goldenen Regel aus der Theorie: **Die Datenbank ist niemals öffentlich erreichbar.** (Die Datenbank selbst kommt erst in KN06 – die Sicherheitsarchitektur steht ab jetzt bereit.)

**Abgaben (B2):**

- Erklärung (2–3 Sätze): Warum ist «3306 nur von SG-Web» sicherer als «3306 vom ganzen Subnetz»?

### B3) Zwei Instanzen mit festen privaten IPs

- **web**: Ubuntu 26.04, `t3.micro`, in Ihrem Subnetz (`subnet_id`), mit fester privater IP (`private_ip`, Ihre Gruppen-IP), SG-Web, und einer Kopie Ihres cloud-init-Templates, erweitert um das Paket `apache2`.
- **intern**: gleich, aber mit der zweiten Gruppen-IP, SG-Intern und Ihrem unveränderten Template. Ergänzen Sie im Template das Paket `netcat-openbsd` (brauchen Sie für den Verbindungstest – und ab jetzt ist es einfach in Ihrem Template).

### B4) Elastic IP für den Webserver

Der Webserver soll unter einer **konstanten** öffentlichen Adresse erreichbar sein:

```hcl
resource "aws_eip" "web" {
  instance = aws_instance.web.id
  tags     = { Name = "IP-Web-<Gruppe>" }
}
```

Geben Sie die Elastic IP und die beiden privaten IPs als Outputs aus.

Führen Sie folgende vier Tests durch und dokumentieren Sie jeweils den Befehl bzw. die URL sowie das Resultat:

2. SSH auf die Web-Instanz funktioniert.
3. **Interner Verbindungstest:** Von der Web-Instanz aus (per SSH eingeloggt) erreichen Sie die Intern-Instanz über deren **private** IP: `nc -zv <private-IP-intern> 22`.

## Häufige Fehlerquellen

- **`InvalidSubnet.Conflict` / CIDR-Überschneidung:** Ihr Subnetz-CIDR kollidiert mit einem bestehenden Subnetz – prüfen Sie, ob Sie wirklich den Gruppen-CIDR verwenden (die Standard-Subnetze belegen die unteren Bereiche der VPC).
- **`InvalidIPAddress.InUse` oder Instanz startet nicht:** Die private IP liegt ausserhalb Ihres Subnetz-CIDR – oder Sie haben eine der von AWS **reservierten** Adressen erwischt (die ersten vier und die letzte IP jedes Subnetzes sind tabu; Ihre Gruppen-Endungen sind bewusst sicher gewählt).
- **Kein SSH auf die Instanzen:** `map_public_ip_on_launch = true` im Subnetz vergessen → die Instanzen haben gar keine öffentliche IP.
- **`nc: command not found`:** Das Paket `netcat-openbsd` fehlt im cloud-init der Intern-Instanz – Datei ergänzen und Instanz neu erstellen (nicht von Hand installieren!).
- **Der Negativtest «funktioniert» sofort mit `connection refused`:** Das wäre sogar ein interessanter Befund – *refused* heisst «Port zu, aber Instanz erreichbar», *timeout* heisst «Security Group blockt». Bei uns läuft (noch) keine Datenbank, die SG blockt vorher → Timeout ist das erwartete Resultat.
- **Elastic-IP-Limit:** Im Learner Lab sind maximal 5 Elastic IPs möglich – alte Experimente aufräumen.
- **`DependencyViolation` beim `destroy`:** Kurz warten und erneut ausführen – AWS gibt Netzwerk-Objekte manchmal verzögert frei.
