# KN03: OpenTofu I – Infrastruktur als Code

**Theorie zu dieser Kompetenz:** [Infrastructure as Code (Überblick)](../Theorie/InfrastructureAsCode.md) · [OpenTofu](../Theorie/OpenTofu.md)

**Werkzeuge:** [OpenTofu installieren](../Tools/OpenTofu.md) · [Credentials-Routine](../Tools/AwsCredentials.md)

Beachten Sie die [allgemeinen Informationen zu den Abgaben](../Abgaben.md).

**Richtzeit:** ca. 5 Lektionen

Bisher haben Sie die **Installation** einer Instanz automatisiert (cloud-init) – die Instanz selbst haben Sie aber noch im GUI zusammengeklickt. Ab jetzt wird auch die **Infrastruktur** zu Code: Instanz, Security Group und alles Weitere entstehen aus `.tf`-Dateien mit OpenTofu. Ab diesem KN gilt: **Infrastruktur wird nie mehr im GUI erstellt** – das GUI dient nur noch zur Verifikation.

## Lernziele

Die Lernziele sind als Selbstcheck formuliert. Prüfen Sie sie **vor der Abgabe**: Jede Aussage, die Sie nicht bestätigen können, ist eine Lücke – und genau dort wird die Lehrperson bei der Abnahme nachfragen.

- [ ] Ich kann die Credentials-Routine im Schlaf und weiss, warum Credentials nie in Code-Dateien gehören.
- [ ] Ich kann den Unterschied zwischen deklarativ und imperativ erklären und OpenTofu, cloud-init und CLI den richtigen Ebenen zuordnen.
- [ ] Ich beherrsche den Zyklus `tofu init` → `plan` → `apply` → `destroy` und kann erklären, was jeder Schritt tut.
- [ ] Ich kann einen Plan **lesen**: Ich erkenne, ob eine Ressource erstellt (`+`), geändert (`~`) oder ersetzt (`-/+`) wird, und kann erklären, warum.
- [ ] Ich kann Ressourcen über Referenzen verknüpfen (z. B. Security Group ↔ Instanz) und erklären, wie OpenTofu daraus die Reihenfolge ableitet.
- [ ] Ich kann erklären, was im State steht, warum er nicht ins Git gehört und was passiert, wenn er verloren geht.
- [ ] Ich kann eine fremde (KI-generierte) Konfiguration kritisch prüfen und Sicherheitsprobleme benennen.



## A) Setup & der Zyklus (20%)

Lesen Sie zuerst die Theorie-Kapitel [Infrastructure as Code](../Theorie/InfrastructureAsCode.md) und [OpenTofu](../Theorie/OpenTofu.md).

### A1) Werkzeuge einrichten

1. Installieren Sie OpenTofu nach der [Anleitung im Tools-Ordner](../Tools/OpenTofu.md) und prüfen Sie die Installation (`tofu -version`).
2. Starten Sie das Learner Lab und führen Sie die [Credentials-Routine](../Tools/AwsCredentials.md) aus. **Ab jetzt ist das Ihr erster Handgriff bei jeder Arbeitssession.**
3. Erstellen Sie in Ihrem Repo den Ordner `KN03/` mit einer `.gitignore` gemäss der Tools-Anleitung (State, `.terraform/`).

**Abgaben (A1):**

- Screenshot von `tofu -version`.

### A2) Der Zyklus mit einer einzigen Ressource

Sie beginnen bewusst klein – eine einzelne Security Group, damit Sie sich auf den **Arbeitszyklus** konzentrieren können:

1. Erstellen Sie `main.tf` mit dem `terraform`-Block, dem `provider`-Block (Region `us-east-1`) und einer Security Group, die Port 22 und 80 eingehend erlaubt (Vorlage: Theorie-Kapitel). Benennen Sie die Security Group **`KN03-SG-<Ihr Vorname>`** (Tag `Name`) – damit im Abgabe-Screenshot eindeutig ersichtlich ist, dass Sie diese Sicherheitsgruppe selbst erstellt haben.
2. `tofu init` – schauen Sie sich an, was heruntergeladen wurde (Ordner `.terraform/`).
3. `tofu plan` – **lesen Sie die Ausgabe Zeile für Zeile**, bevor Sie weitermachen.
4. `tofu apply` – und verifizieren Sie die Security Group **im AWS-GUI**.
5. Führen Sie `tofu plan` **erneut** aus. Was zeigt der Plan jetzt an, und warum? (Stichwort aus der Theorie: deklarativ/Idempotenz.)
6. Ändern Sie die Beschreibung eines Ports, `tofu plan` – wie wird die Änderung dargestellt?
7. `tofu destroy` – und verifizieren Sie im GUI, dass die Security Group weg ist.

**Abgaben (A2):**

- Ihre `main.tf` aus A2 als Datei im Repo.
- Screenshot des ersten `plan` (Ausschnitt mit dem `+ create`).
- Screenshot aus AWS-EC, der die erstellte Sicherheitsgruppe zeigt – mit sichtbarem Namen `KN03-SG-<Ihr Vorname>`.
- Antwort in Ihrer Doku: Was zeigt `tofu plan` direkt nach einem erfolgreichen `apply`, und wieso ist genau das der Kernunterschied zu einem Bash-Skript mit CLI-Befehlen?



## B) Instanz + Security Group + cloud-init als Code (45%)

Jetzt bauen Sie die komplette Umgebung aus KN02 Teil C – aber vollständig als Code, ohne einen einzigen GUI-Klick.

### B1) Die Konfiguration

Erweitern Sie Ihr Projekt (Sie dürfen alles in `main.tf` halten oder in mehrere Dateien aufteilen, z. B. `providers.tf`, `main.tf`, `outputs.tf`):

- **Security Group** mit eingehend Port 22 (SSH) und Port 80 (HTTP), ausgehend alles.
- **Instanz**: Ubuntu Server 26.04 (AMI-ID für `us-east-1` selbst nachschlagen – z. B. im EC2-GUI unter AMI Catalog), Typ `t3.micro`.
- **cloud-init**: Ihr Template aus KN02 wird als `user_data` übergeben (`file("cloud-init-template.yaml")`). Kein Key Pair im GUI nötig – Ihre Schlüssel kommen ja aus dem cloud-init!
- **Referenz**: Die Instanz verwendet die Security Group über deren Referenz (`aws_security_group.<name>.id`) – keine hartcodierte ID.
- **Output**: Die öffentliche IP der Instanz wird als Output ausgegeben.

Führen Sie `plan` und `apply` aus und weisen Sie nach:

- SSH-Login mit Ihrem Schlüssel als Ihr cloud-init-Benutzer funktioniert.
- Das cloud-init hat gegriffen (Log oder eine Ihrer Erweiterungen).

**Abgaben (B1):**

- Alle `.tf`-Dateien und die cloud-init-Datei im Repo (kommentiert – Sie müssen jede Zeile erklären können).
- Screenshot: `tofu apply`-Zusammenfassung (`Apply complete! Resources: ...`) und der Output mit der öffentlichen IP.
- Screenshot: SSH-Login auf die Instanz.
- Erklärung in Ihrer Doku (2–3 Sätze): Wie «weiss» OpenTofu, dass es die Security Group **vor** der Instanz erstellen muss?

### B2) Änderungen beobachten: ändern vs. ersetzen

Führen Sie **nacheinander** zwei Änderungen durch und beobachten Sie jeweils **zuerst den Plan**, bevor Sie bestätigen:

1. Ändern Sie den **Namen (Tag)** der Instanz → was sagt der Plan?
2. Ändern Sie etwas in der **cloud-init-Datei** (z. B. ein zusätzliches Paket) → was sagt der Plan jetzt, und **warum ist diese Änderung fundamental anders**?

**Abgaben (B2):**

- Screenshot des Plans für die erste Änderung aus B2 (der relevante Ausschnitt genügt).
- Screenshot des Plans für die zweite Änderung aus B2 (der relevante Ausschnitt genügt).
- Erklärung in Ihrer Doku (3–5 Sätze): Warum führt die cloud-init-Änderung zu `destroy and then create replacement`, die Tag-Änderung aber nur zu `update in-place`?



## C) Zerstören ohne Angst: Reproduzierbarkeit & der State (25%)

Der Moment, für den Sie das alles lernen: **Ihre Umgebung ist reproduzierbar – Sie können sie jederzeit ohne Angst wegwerfen und neu aufbauen.**

### C1) Alles weg, alles wieder da

1. Zerstören Sie Ihre komplette Umgebung **absichtlich und vollständig**: `tofu destroy`. Verifizieren Sie im GUI: Es ist wirklich alles weg.
2. Stellen Sie die komplette Umgebung mit **einem Befehl** wieder her. Stoppen Sie die Zeit (Ihre aktive Arbeitszeit!).
3. Vergleichen Sie: Wie lange hätten Sie in KN02 gebraucht, um Instanz, Security Group und cloud-init im GUI wieder zusammenzuklicken? Und: Wären Sie sicher, dass die neue Umgebung **exakt gleich** konfiguriert wäre?

**Abgaben (C1):**

- Beide Zeiten (Wiederherstellung per Code vs. Ihre Schätzung für GUI) mit 2–3 Sätzen Interpretation.

### C2) State verstehen

1. **Drift-Experiment:** Terminieren Sie Ihre Instanz von Hand **im AWS-GUI** (genau das, was man nie tun sollte). Führen Sie danach `tofu plan` aus. Was stellt OpenTofu fest, und was schlägt es vor?
2. Reparieren Sie die Situation mit `tofu apply`.

**Abgaben (C2):**

- Screenshot des `tofu plan` nach dem Drift-Experiment mit Erklärung (2–3 Sätze): Woher weiss OpenTofu, dass die Instanz fehlt?
- Antwort in Ihrer Doku: Nennen Sie zwei Gründe, warum `terraform.tfstate` nicht ins Git-Repository gehört.



## D) KI-Review: fremden Code beurteilen (10%)

Ein Kollege hat sich von einer KI eine Konfiguration für einen **Datenbank-Server** generieren lassen ([review-config.tf](./KN03/review-config.tf)) und behauptet: «Läuft doch – die KI wird schon wissen, was sie tut.»

Analysieren Sie die Datei, **ohne sie auszuführen**. Sie enthält **mehrere** Probleme – von «funktioniert bei uns nicht» bis «grobes Sicherheitsloch». Nutzen Sie Ihr Wissen aus diesem KN und aus der Theorie ([Netzwerk und Sicherheit](../Theorie/NetzwerkSicherheit.md) hilft ebenfalls).

**Abgaben:**

- Ihre Review als Markdown: Liste aller gefundenen Probleme, je mit **Begründung** (warum ist das ein Problem?) und **Korrektur** (wie gehört es richtig?). Ordnen Sie die Funde nach Schweregrad.
- Die korrigierte Konfiguration als Datei im Repo (ausführen müssen Sie sie nicht).



## Häufige Fehlerquellen

- **`ExpiredToken` / `InvalidClientTokenId`:** Das Lab wurde neu gestartet, die Credentials nicht – [Routine](../Tools/AwsCredentials.md) ausführen.
- **`UnauthorizedOperation`:** Diese Aktion erlaubt das Learner Lab nicht (typisch: IAM-Ressourcen). Konfiguration überdenken.
- **AMI-Fehler:** AMI-IDs gelten **pro Region**. Eine AMI-ID aus einem Tutorial (andere Region) funktioniert in `us-east-1` nicht.
- **SSH geht nicht nach `apply`:** Erst 1–2 Minuten warten (cloud-init läuft noch), dann Security Group (Port 22?), Benutzername und Schlüssel prüfen. Log: `/var/log/cloud-init-output.log`.
- **`apply` hängt bei `Still creating...`:** Normal für Instanzen (bis ~1 Minute). Deutlich länger → Abbrechen vermeiden, warten; notfalls im GUI den Instanz-Status prüfen.
- **Versehentlich State gelöscht/kaputt:** Nicht blind weitermachen – siehe [Tools-Anleitung](../Tools/OpenTofu.md), Abschnitt «Häufige Probleme».
- **Zwei Umgebungen doppelt:** Sie haben im GUI *und* per OpenTofu Ressourcen erstellt. Das GUI ist ab jetzt nur noch zum Anschauen da – Aufräumen nicht vergessen (Budget!).
