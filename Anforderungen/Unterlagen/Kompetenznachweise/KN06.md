# KN06: Ansible – Konfiguration im Betrieb

Beachten Sie die [allgemeinen Informationen zu den Abgaben](../Abgaben.md).

**Richtzeit:** ca. 6 Lektionen

Ihre Werkzeugkiste ist fast komplett: OpenTofu baut die Infrastruktur, cloud-init richtet Instanzen beim ersten Boot ein. Was fehlt: **laufende Server wiederholbar konfigurieren** – Software installieren, Konfigurationen ändern, und das auf mehreren Servern gleichzeitig. Genau dafür ist Ansible da. Sie installieren in dieser Kompetenz den klassischen Web+DB-Stack (Apache, PHP, MariaDB) – zuerst einmal von Hand, um den Schmerz zu spüren, dann als Playbook.

**Theorie zu dieser Kompetenz:** [Ansible](../Theorie/Ansible.md) · [Infrastructure as Code](../Theorie/InfrastructureAsCode.md)

**Werkzeuge:** [Ansible installieren](../Tools/Ansible.md) (Windows: via WSL!)

## Lernziele

Die Lernziele sind als Selbstcheck formuliert. Prüfen Sie sie **vor der Abgabe**: Jede Aussage, die Sie nicht bestätigen können, ist eine Lücke – und genau dort wird die Lehrperson bei der Abnahme nachfragen.

- [ ] Ich kann die Arbeitsteilung OpenTofu / cloud-init / Ansible erklären und begründen, welches Werkzeug wofür zuständig ist.
- [ ] Ich kann ein Inventar schreiben und die Verbindung zu den Zielservern testen.
- [ ] Ich kann ein Playbook mit mehreren Plays, Variablen, Templates und Handlers schreiben und jede Zeile erklären.
- [ ] Ich kann erklären, warum ein Handler nur bei Änderungen ausgelöst wird – und warum das besser ist als ein Restart-Task am Ende.
- [ ] Ich kann Idempotenz erklären und am Output (`changed=0`) nachweisen.
- [ ] Ich kann die Pakete des Stacks erklären: wozu braucht es *apache2*, *php*, *libapache2-mod-php*, *mariadb-server*, *php-mysql*?
- [ ] Ich kann ein fremdes (KI-generiertes) Playbook kritisch beurteilen und `shell`-Tasks durch die richtigen Module ersetzen.
- [ ] Ich kann ein EBS-Volume mit den Modulen `filesystem` und `mount` idempotent einbinden – und erklären, warum Idempotenz hier Daten schützt.



## Vorbereitung: Die Infrastruktur steht schon

Sie verwenden Ihr **OpenTofu-Projekt aus KN04** wieder: eigenes Subnetz, Web-Instanz (SG mit 22/80, Elastic IP) und Intern-Instanz (SG mit 22, Port 3306 nur von SG-Web). Die Intern-Instanz wird heute zur **Datenbank-Instanz**. Führen Sie `tofu apply` aus – die Umgebung steht in zwei Minuten (genau dafür haben Sie KN03 gemacht).

**Wichtig:** Die cloud-init-Dateien bleiben schlank (Schlüssel, Härtung, `netcat-openbsd`). Apache können Sie aus dem Web-cloud-init entfernen – **die Installation übernimmt heute Ansible.** Damit ist die Arbeitsteilung sauber: cloud-init = Boot-Grundausstattung, Ansible = Applikations-Stack.



## A) Kontrastlektion: einmal von Hand (15%)

Bevor Sie automatisieren, machen Sie es **ein einziges Mal** von Hand – damit Sie wissen, was Ansible Ihnen abnimmt. **Starten Sie jetzt eine Stoppuhr.** Loggen Sie sich per SSH ein und führen Sie aus:

**Auf der Web-Instanz:**

```bash
sudo apt update
sudo apt install -y apache2 php libapache2-mod-php php-mysql
sudo systemctl restart apache2
echo "<?php phpinfo(); ?>" | sudo tee /var/www/html/info.php
```

**Auf der DB-Instanz:**

> [!IMPORTANT]
>
> **Achtung**: Passwort ändern

```bash
sudo apt update
sudo apt install -y mariadb-server
sudo mysql -u root -e "GRANT ALL ON *.* TO 'admin'@'%' IDENTIFIED BY 'IhrPasswort' WITH GRANT OPTION;"
sudo sed -i 's/127.0.0.1/0.0.0.0/g' /etc/mysql/mariadb.conf.d/50-server.cnf
sudo systemctl restart mariadb
```

**Stoppen Sie jetzt die Stoppuhr** – sobald beide Instanzen wie oben konfiguriert sind. Das ist Ihre gemessene Zeit für die Abgabe; der «Nachweis der Handarbeit» danach zählt nicht mehr dazu (den vergleichen Sie in D2 mit der automatisierten Variante).

Sie müssen diese Befehle **verstehen** – die Lehrperson wird Sie dazu befragen: Was installiert welches Paket? Was macht der GRANT-Befehl? Warum die `sed`-Änderung an der `bind-address` (Theorie: [Stationen einer Anfrage](../Theorie/NetzwerkSicherheit.md))? **Passwort-Regel:** etwas Einzigartiges, kein privates Passwort – es wird für die Lehrperson sichtbar sein.

**Nachweis der Handarbeit** (dieser Teil ist nur erbracht, wenn er tatsächlich von Hand gemacht wurde – Automatisierung kommt in Teil C früh genug):

1. Loggen Sie sich auf der DB-Instanz **interaktiv** in die Datenbank ein (`mysql -u admin -p`, Passwort am Prompt eintippen) und führen Sie diese Abfrage aus – sie stempelt Ihren Namen und den Zeitpunkt:
   `SELECT NOW() AS zeitpunkt, USER() AS benutzer, '<IhrVorname>' AS bearbeitet_von;`
2. Rufen Sie **auf beiden Instanzen** am Schluss `history` auf. Die History zeigt alle interaktiv getippten Befehle dieser Session – bei einer automatisierten Ausführung wäre sie leer. Genau deshalb ist sie Ihr Beleg.

Und jetzt der Punkt der Übung: Ersetzen Sie **beide Instanzen** (`tofu apply -replace=...`). Ihre ganze Handarbeit ist weg. Zeit für Ansible.

**Abgaben:**

- Ihre gemessene Zeit für die Handarbeit.
- Kurze Erklärung (je 1 Satz) zu den fünf Paketen und zur `bind-address`-Änderung (`sed` Befehl).
- Screenshot der interaktiven mysql-Session: Passwort-Prompt und Resultat Ihrer Stempel-Abfrage sichtbar.
- Screenshots der `history`-Ausgabe beider Instanzen (die relevanten Befehle sichtbar).
- Screenshot: Output von `tofu apply -replace=...` mit den Outputs (neue IPs) – Sie brauchen diese IPs gleich für das Inventar in Teil B.



## B) Ansible einrichten & Verbindung testen (10%)

Installieren Sie Ansible nach der [Tools-Anleitung](../Tools/Ansible.md) – unter Windows via WSL, inklusive der Schlüssel-Kopie ins WSL-Home.

Erstellen Sie im Repo den Ordner `KN06/` mit `ansible.cfg` (siehe Tools-Anleitung) und dem Inventar `inventory.ini`:

```ini
[web]
<öffentliche-IP-web> ansible_user=<IhrUser> ansible_ssh_private_key_file=~/.ssh/vorname1.pem

[db]
<öffentliche-IP-db> ansible_user=<IhrUser> ansible_ssh_private_key_file=~/.ssh/vorname1.pem
```

Testen Sie die Verbindung: `ansible all -m ping` – beide Hosts müssen mit `pong` antworten.

**Abgaben:**

- `ansible.cfg` und `inventory.ini` im Repo (Screenshot der IPs genügt nicht – Dateien!).
- Screenshot des erfolgreichen `ansible all -m ping`.



## C) Der Stack als Playbook (40%)

Jetzt bauen Sie die Handarbeit aus Teil A als Playbook `site.yaml` mit **zwei Plays** nach. Halten Sie sich an die Regel aus der Theorie: **erst das passende Modul, `shell` ist der letzte Ausweg.**

### Play 1: Datenbank (hosts: db)

- Pakete: `mariadb-server` und `python3-pymysql` (Letzteres braucht das Ansible-MySQL-Modul) → Modul `apt`.
- `bind-address` auf `0.0.0.0` ändern → Modul `replace` oder `lineinfile` (Datei: `/etc/mysql/mariadb.conf.d/50-server.cnf`) → `notify` auf einen Handler «MariaDB neustarten».
- Admin-Benutzer idempotent erstellen → Modul `community.mysql.mysql_user`:

```yaml
    - name: Admin-Benutzer erstellen
      community.mysql.mysql_user:
        name: admin
        password: "{{ db_password }}"
        priv: "*.*:ALL,GRANT"
        host: "%"
        login_unix_socket: /run/mysqld/mysqld.sock
```

### Play 2: Webserver (hosts: web)

- Pakete: `apache2`, `php`, `libapache2-mod-php`, `php-mysql` → Modul `apt`.
- `info.php` erstellen → Modul `copy` (mit `content:`).
- `db.php` aus dem Template [db.php.j2](./KN06/db.php.j2) erzeugen → Modul `template`. Schauen Sie sich das Template an: Die Platzhalter `{{ db_host }}`, `{{ db_user }}`, `{{ db_password }}` füllt Ansible aus Ihren **Variablen**.
- Handler «Apache neustarten».

### Variablen

Definieren Sie die Variablen zentral (z. B. in `group_vars/all.yaml`): `db_host` (die **private** IP Ihrer DB-Instanz – aus Ihrem tofu-Output), `db_user`, `db_password`. Überlegen Sie: Warum die private und nicht die öffentliche IP? (Ihre Security Group aus KN04 kennt die Antwort.)

### Ausführen und testen

`ansible-playbook site.yaml` – und dann Ihre Testfälle (vorher definieren!):

1. `http://<Elastic-IP>/` → Apache-Startseite.
2. `http://<Elastic-IP>/info.php` → PHP-Infoseite.
3. `http://<Elastic-IP>/db.php` → Liste der DB-Benutzer. **Das ist der Moment:** Der Webserver spricht über die private IP mit der Datenbank, durch die Security-Group-Regel aus KN04 (3306 nur von SG-Web).
4. Negativtest aus KN04 erneut: Port 3306 von Ihrem Laptop → Timeout.

**Abgaben:**

- `site.yaml`, `group_vars/all.yaml` (Passwort darf hier drinstehen – siehe Passwort-Regel) und das Template im Repo, kommentiert.
- Screenshot: Playbook-Lauf mit der `PLAY RECAP` (beide Hosts, `failed=0`).
- Screenshots der Testfälle 1–3 (URL sichtbar) und 4.
- Erklärung (2–3 Sätze): Warum steht in `db_host` die private IP?
- Erklärung (2–3 Sätze): Wozu dient das `template`-Modul, und warum wäre `copy` hier die falsche Wahl?



## D) Idempotenz beweisen & KI-Playbook reparieren (25%)

### D1) Der Doppel-Lauf

Führen Sie `ansible-playbook site.yaml` **direkt nochmals** aus. Ziel: `changed=0` auf beiden Hosts. Falls ein Task bei jedem Lauf `changed` meldet, ist er nicht idempotent – finden und beheben Sie die Ursache.

Weisen Sie ausserdem die Handler-Logik nach: Ändern Sie etwas am `db.php.j2`-Template (z. B. die Überschrift), führen Sie das Playbook aus und beobachten Sie: Welche Tasks melden `changed`? Wurde Apache neu gestartet? Und beim nächsten Lauf ohne Änderung?

**Abgaben (D1):**

- Screenshot: zweiter Lauf mit `changed=0` (PLAY RECAP).
- Screenshot nach Template-Änderung un Ansible Playbook Ausführung und 2–3 Sätze zum Handler-Nachweis (wann lief der Neustart, wann nicht?).

### D2) Die Nagelprobe

Ersetzen Sie **beide Instanzen** erneut (`tofu apply -replace=...`), passen Sie die neuen öffentlichen IPs im Inventar an (und `db_host`, falls sich die private IP geändert hat – hat sie?), und führen Sie das Playbook aus. Von leeren Instanzen zum laufenden Stack: **ein Befehl.** Stoppen Sie die Zeit und vergleichen Sie mit Teil A.

**Abgaben (D2):**

- Screenshot: Output von `tofu apply -replace=...` mit den Outputs (neue IPs) – damit passen Sie Inventar und `db_host` an und testen anschliessend erneut.
- Ihre gemessene Zeit aus D2, zusammen mit der Zeit aus Teil A im Vergleich, mit 2–3 Sätzen Fazit.
- Antwort zur privaten IP in D2: geändert oder nicht – und warum? (KN04 lässt grüssen.)

### D3) KI-Review: das Shell-Playbook

Ein Kollege hat sich von einer KI ein Playbook generieren lassen: [broken-playbook.yaml](./KN06/broken-playbook.yaml). Es läuft fehlerfrei durch – und ist trotzdem schlechtes Ansible.

- Führen Sie es gedanklich (oder real gegen Ihre Web-Instanz) **zweimal** aus: Was melden die Tasks beim zweiten Lauf, und warum ist das ein Problem?
- Welcher Task verursacht bei **jedem** Lauf eine kurze Downtime, obwohl sich nichts geändert hat?
- Schreiben Sie das Playbook so um, dass es idempotent ist und die richtigen Module verwendet.

**Abgaben (D3):**

- Ihre Analyse des KI-Playbooks (3 Befunde mit Begründung) und die korrigierte Version als Datei im Repo.



## E) Das KN05-Versprechen einlösen: Speicher idempotent einbinden (10%)

In KN05 haben Sie das EBS-Volume **von Hand** formatiert und gemountet – mit dem Versprechen, dass man das in der Praxis mit Prüflogik automatisiert. Jetzt haben Sie das Werkzeug dafür:

1. Ergänzen Sie in Ihrem OpenTofu-Projekt ein 5-GB-Volume samt Attachment an die DB-Instanz (kennen Sie aus KN05).
2. Ergänzen Sie im DB-Play zwei Tasks:
   - Modul `filesystem` (fstype `ext4`, dev `/dev/nvme1n1`) – **formatiert nur, wenn die Disk noch kein Dateisystem hat.**
   - Modul `mount` (path `/data`, `state: mounted`) – mountet **und** trägt das Volume in `/etc/fstab` ein; damit ist auch das «Mount weg nach Neustart»-Problem aus KN05 gelöst.
3. Der Beweis, dass Idempotenz hier Daten **schützt**: Datei auf `/data` anlegen, Playbook erneut ausführen – `changed=0`, kein Format, Datei lebt. Genau der Unterschied zu einem Skript mit blindem `mkfs`.

**Abgaben:**

- Die beiden Tasks im Playbook und die Volume-Ergänzung in den `.tf`-Dateien.
- Screenshot des zweiten Laufs (`changed=0`) und der überlebenden Datei auf `/data`.
- Erklärung (2–3 Sätze): Warum wäre derselbe Ablauf mit einem `shell: mkfs...`-Task gefährlich gewesen?

## Häufige Fehlerquellen

- **`UNREACHABLE` nach dem Instanz-Replace:** Die öffentlichen IPs im Inventar sind veraltet – nachführen. (Wer das leid ist: Die Elastic IP der Web-Instanz bleibt ja konstant …)
- **WSL: `Permission denied (publickey)`:** Schlüssel liegt noch unter `/mnt/c/...` – ins WSL-Home kopieren und `chmod 400` (siehe [Tools-Anleitung](../Tools/Ansible.md)).
- **`Failed to lock apt`:** Die frische Instanz führt noch automatische Updates aus – 1–2 Minuten warten, nochmals ausführen.
- **`mysql_user` schlägt fehl:** Paket `python3-pymysql` fehlt auf der DB-Instanz, oder der `login_unix_socket`-Parameter fehlt (ohne ihn versucht Ansible einen Passwort-Login als root).
- **db.php zeigt `Verbindung fehlgeschlagen`:** Die vier Schichten aus der [Theorie](../Theorie/NetzwerkSicherheit.md) durchgehen: SG-Regel (3306 von SG-Web?), richtige (private!) IP in `db_host`, läuft MariaDB (`systemctl status`), `bind-address` wirklich geändert und Service neu gestartet?
- **Task meldet immer `changed`:** Typisch bei `shell`/`command` – aufs passende Modul umstellen; genau das ist die Lektion aus D3.
- **`community.mysql` nicht gefunden:** Sie haben das schlanke `ansible-core` installiert statt `ansible` – Collection nachinstallieren: `ansible-galaxy collection install community.mysql`.
- **`InvalidParameterValue: availabilityZone` beim `apply` von Teil E:** Nicht mit KN05 verwechseln! In KN05 gab es **kein** Subnetz, darum wurde dort die AZ direkt an der Instanz gepinnt. Hier in KN06 haben Sie aus KN04 bereits ein eigenes `aws_subnet` – und ein Subnetz liegt immer fest in **einer** AZ. Pinnen Sie die AZ deshalb am **Subnetz** (`availability_zone = "us-east-1a"` bei `aws_subnet`), **nicht** zusätzlich an der Instanz: Ein eigener AZ-Wert an der Instanz, der von der (automatisch gewählten) AZ Ihres Subnetzes abweicht, führt genau zu diesem Fehler. Ohne Subnetz-Pin würde AWS die AZ des Subnetzes einmalig selbst wählen – das reicht für die `-replace`-Sicherheit hier sogar aus, weil ein reiner Instanz-Replace das Subnetz nicht anfasst; der explizite Pin macht das Ergebnis nur zusätzlich reproduzierbar.
