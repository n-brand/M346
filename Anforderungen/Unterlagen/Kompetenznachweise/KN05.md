# KN05: Speicher als Code

Beachten Sie die [allgemeinen Informationen zu den Abgaben](../Abgaben.md).

**Richtzeit:** ca. 3 Lektionen

Sie wissen inzwischen: Instanzen sind Wegwerfprodukte – wir ersetzen sie, statt sie zu reparieren. Aber was passiert dabei mit den **Daten**? In dieser Kompetenz erleben Sie den Unterschied zwischen flüchtigem und persistentem Speicher am eigenen Leib – und lernen die Speichermodelle kennen, indem Sie sie als Code erstellen und benutzen.

**Theorie zu dieser Kompetenz:** [Speichermodelle](../Theorie/Speichermodelle.md) · [OpenTofu](../Theorie/OpenTofu.md)

## Lernziele

## A) Das Persistenz-Experiment (30%)

## B) Persistenter Speicher als Code (50%)

Jetzt sorgen Sie dafür, dass Daten das Ersetzen der Instanz überleben – auf zwei Arten.

### B1) Blockspeicher: EBS-Volume anhängen

Erweitern Sie Ihre Konfiguration um ein separates Volume und dessen Verbindung zur Instanz:

```hcl
resource "aws_ebs_volume" "daten" {
  availability_zone = aws_instance.speicher.availability_zone  # muss zur Instanz passen!
  size              = 5
  type              = "gp3"

  tags = { Name = "KN05-Daten" }
}

resource "aws_volume_attachment" "daten" {
  device_name = "/dev/sdf"
  volume_id   = aws_ebs_volume.daten.id
  instance_id = aws_instance.speicher.id
}
```

**Wichtig:** Pinnen Sie zusätzlich die Availability Zone Ihrer Instanz fest, z. B. `availability_zone = "us-east-1a"` bei `aws_instance.speicher`. Ohne diesen fixen Wert kann AWS die Instanz bei einem späteren `-replace` in einer anderen AZ neu starten – und weil die AZ eines EBS-Volumes unveränderlich ist, würde das `aws_ebs_volume.daten` zwingen, ebenfalls neu (und leer!) erstellt zu werden, obwohl nur die Instanz ersetzt werden sollte.

Nach dem `apply` binden Sie das Volume **auf der Instanz** ein. Das machen wir heute bewusst von Hand: Formatieren ist eine Operation auf den **Daten**, und ein `mkfs` im falschen Moment wäre fatal. In der Praxis automatisiert man das natürlich trotzdem – aber mit Werkzeugen, die eingebaute Prüflogik haben. **Dieses Versprechen lösen wir in KN06 ein**, wenn Sie Ansible kennen: Dort gibt es ein Modul, das nur formatiert, wenn die Disk wirklich leer ist.

```bash
lsblk                          # Welche Disk ist neu? (bei t3-Instanzen z. B. nvme1n1 - NICHT die Root-Disk!)
sudo mkfs.ext4 /dev/nvme1n1    # NUR die neue, leere 5-GB-Disk formatieren - Doppelcheck mit lsblk!
sudo mkdir /data
sudo mount /dev/nvme1n1 /data
echo "Kundendaten März" | sudo tee /data/wichtig.txt
```

Wiederholen Sie jetzt das Experiment aus A: Instanz ersetzen (`-replace`), auf der neuen Instanz das Volume wieder mounten (**ohne** `mkfs` – warum?), und prüfen Sie den Inhalt von `/data/wichtig.txt`.

**Abgaben (B1):**

- Alle `.tf`-Dateien und das  cloud-init im Repo (kommentiert).
- Screenshot B1: `lsblk`, das gemountete Volume, und `/data/wichtig.txt` **nach** dem Instanz-Replace. (alle Befehle in einem Screenshot)
- Antwort: Warum darf auf der neuen Instanz kein `mkfs` mehr ausgeführt werden?

### B2) Objektspeicher: S3-Bucket

**Normalerweise** würden Sie den Bucket genau gleich deklarativ erstellen wie das EBS-Volume in B1:

```hcl
resource "aws_s3_bucket" "backup" {
  bucket        = "kn05-<vorname>-<zufallszahl>"  # global eindeutig, nur Kleinbuchstaben!
  force_destroy = true                            # erlaubt destroy trotz Inhalt
}
```

**Im aktuellen Learner Lab funktioniert das nicht:** Der Terraform-AWS-Provider versucht ein (veraltetes) Attribut zu befüllen und blockiert damit die Ausführung.  Das ist eine Einschränkung der Lernumgebung, keine, die Sie durch eigenen Code oder zusätzliche Rechte beheben können.

**Deshalb weichen wir hier aus:** Erstellen Sie den Bucket von Hand im AWS-Konsole (S3 → Create bucket), Name `kn05-<vorname>-<zufallszahl>` (global eindeutig, nur Kleinbuchstaben, Zahlen, Bindestriche), alle übrigen Einstellungen auf Standard belassen. In Terraform referenzieren Sie ihn nur noch, statt ihn zu erstellen:

```hcl
data "aws_s3_bucket" "backup" {
  bucket = "kn05-<vorname>-<zufallszahl>"  # muss exakt dem manuell erstellten Bucket entsprechen
}
```

Eine Datenquelle (`data`) liest nur Basisinformationen zu einer bereits existierenden Ressource – hier Region und Domain-Name – und ist von der oben genannten Sperre nicht betroffen. Wichtig: Der Bucket muss existieren, **bevor** Sie `tofu apply` ausführen, sonst meldet die Datenquelle einen Fehler (siehe Häufige Fehlerquellen).

Damit die **Instanz** auf den Bucket zugreifen darf, braucht sie eine Berechtigung – im Learner Lab das vorgefertigte Instance Profile. Ergänzen Sie bei Ihrer Instanz:

```hcl
  iam_instance_profile = "LabInstanceProfile"
```

Fügen Sie dem cloud-init das Paket `awscli` hinzu (die Instanz wird dadurch ersetzt – inzwischen Routine). Dann, auf der Instanz **manuell** ausführen:

```bash
aws s3 cp /data/wichtig.txt s3://<ihr-bucket-name>/
aws s3 ls s3://<ihr-bucket-name>/
```

Beachten Sie: Sie haben auf der Instanz **keine Credentials** eingerichtet – der Zugriff funktioniert über das Instance Profile (die Instanz «ist» eine Rolle). Erklären Sie in der Doku, warum das sicherer ist, als Ihre Credentials auf die Instanz zu kopieren.

**Abgaben (B2):**

- Alle `.tf`-Dateien und das erweiterte cloud-init im Repo (kommentiert).
- Screenshot: erfolgreicher `aws s3 cp`.
- Screenshot: Bucket-**Inhalt** aus dem **AWS-GUI** (nicht Konsole) – als Beweis, dass der Bucket existiert und die Datei enthält.
- Erklärung: Warum ist das Instance Profile sicherer als kopierte Credentials? (2–3 Sätze)

## Häufige Fehlerquellen

- **Storage-Tab: «Delete on termination» mit «Multi-Attach enabled» verwechselt:** In den Volume-Details der Instanz stehen mehrere Checkboxen nahe beieinander. Verantwortlich für das flüchtige Verhalten der Root-Disk ist **«Delete on termination»** (löscht das EBS-Volume beim Terminieren der Instanz mit). **«Multi-Attach enabled»** ist ein unabhängiges Attribut, das nur bei io1/io2-Volumes erlaubt, dasselbe Volume an mehrere Instanzen gleichzeitig anzuhängen – damit hat es nichts zu tun.
- **`-replace` mit dem AWS-Namen-Tag statt der Ressourcen-Adresse:** `tofu apply -replace="aws_instance.KN05-Speicher"` (der Wert aus `tags.Name`) funktioniert **nicht** – OpenTofu erwartet die Adresse aus dem Code, also `<Ressourcentyp>.<Name im resource-Block>`, hier `aws_instance.speicher`. Bei einer falschen Adresse kommt keine Fehlermeldung, der Befehl läuft einfach ins Leere («No changes»).
- **`VolumeInUse` / Volume und Instanz in verschiedenen AZs:** Ein EBS-Volume kann nur an Instanzen in **derselben** Availability Zone hängen – darum die Referenz `aws_instance.<name>.availability_zone` beim Volume statt eines fixen Werts. **Aber:** Das reicht allein nicht – pinnen Sie zusätzlich die AZ der **Instanz selbst** fest (`availability_zone = "us-east-1a"` o. ä.). Sonst kann AWS die Instanz bei einem `-replace` in eine andere AZ verschieben, und weil die AZ eines EBS-Volumes unveränderlich ist, erzwingt das ein Neu-Erstellen (= leeres!) Volume – genau das Gegenteil dessen, was dieses KN zeigen soll.
- **Falsche Disk formatiert:** `lsblk` **vor** jedem `mkfs`! Die Root-Disk erkennen Sie an der Grösse und den Partitionen – die neue Disk ist leer und exakt 5 GB.
- **Device heisst nicht `/dev/sdf`:** Auf modernen Instanztypen (t3) erscheint das Volume als NVMe-Gerät (`/dev/nvme1n1`), egal was im Attachment steht. `lsblk` zeigt die Wahrheit.
- **Mount weg nach Neustart:** `mount` gilt nur bis zum nächsten Boot. Für dieses KN reicht das; dauerhaft bräuchte es einen Eintrag in `/etc/fstab` – genau das erledigt in KN06 (Teil E) das Ansible-Modul `mount` für Sie.
- **`BucketAlreadyExists`:** Bucket-Namen sind **weltweit** eindeutig – Zufallszahl anhängen. Nur Kleinbuchstaben, Zahlen und Bindestriche.
- **`NoSuchBucket` bei `tofu apply`:** Die `data "aws_s3_bucket"`-Datenquelle findet den Bucket nicht. Meist wurde er noch nicht (oder mit falschem/falsch geschriebenem Namen) manuell im AWS-Konsole erstellt – Bucket zuerst anlegen, danach `tofu apply`.
- **`AccessDenied ... GetBucketObjectLockConfiguration` bei `tofu apply`:** Sie haben den Bucket als `resource "aws_s3_bucket"` statt als `data`-Quelle deklariert. Dieser API-Aufruf ist im Learner Lab per Service Control Policy gesperrt und lässt sich nicht durch zusätzliche Rechte beheben – verwenden Sie stattdessen die `data`-Variante wie oben beschrieben.
- **`Access Denied` bei `aws s3 cp`:** Das `iam_instance_profile = "LabInstanceProfile"` fehlt auf der Instanz – oder die Instanz wurde nach der Änderung nicht ersetzt.
- **`/data` existiert nicht (mehr) in B2:** Das Ergänzen von `awscli` im cloud-init ersetzt die Instanz erneut. Die neue Instanz hat eine frische, leere Root-Disk – `/data` muss wie in B1 erneut angelegt und gemountet werden (ohne `mkfs`!), bevor `aws s3 cp` funktioniert.
- **Volume überlebt den `destroy` nicht – war das nicht persistent?** Persistent heisst «überlebt die Instanz», nicht «überlebt `tofu destroy`». Der `destroy` entfernt bewusst **alles**, was das Projekt erstellt hat – auch die Daten. In der Praxis schützt man solche Ressourcen (z. B. `prevent_destroy`) – gute Zusatzfrage für die Abnahme.
